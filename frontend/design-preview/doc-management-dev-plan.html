§1口径与范围

「资料管理」在本方案里是一个三段的完整链路，缺任何一段都不闭环。此前提过的「文档管理评分」即针对这一整体。

① 文件中心（录入与维护）

导航「资料维护」→ 视图 #knowledge（index.html:29734）。表 knowledge_assets，管「有什么资料、什么状态、链接是否有效」。

② 资源中心（召回与推荐）

resource-hub.ts 四源合并（文件 / Skill / 知识 / 产品），四路打分，经插件供给扩展右侧「相关文档」面板。

③ 插件训练库（沉淀与复用）

training_library_entries，自动回复与资料推荐的语料来源，与训练档案（风格快照）分工。

范围边界（明确不做）：① 不做模型微调（外部网关无微调通道，权重污染不可回滚）——训练走「语料 + 检索」不走权重；② 不做文件本体的云存储（沿用「只存链接」模式，见 docs/FILE-CENTER-DEVELOPMENT.md）；③ 不动 WhatsApp 多账号与内置浏览器（已暂停）；④ 不为四源中的 Skill / 产品库新增维护界面（本次只治理文件中心，其余三源照常参与召回）。

§3问题清单（14 项闭环断点）

按四个闭环分组。每项都带代码证据与用户可感知的影响——不是「风格不好」，是「链路在这里断了」。

A · 录入闸断点

编号问题证据与影响
G1类目/标签自由文本，无受控词表knowledgeAssetInputSchema（server.ts:1758）对 category 只做非空校验；前端是普通输入框（prototype-api.ts:24527、24533）。同类资料散成「产品知识 / 产品资料 / 产品文档」多个类目，检索时 idf 分母被稀释，报表也按类目聚不起来。
G2无重复检测同标题、同 URL 可反复入库（POST 无任何查重，server.ts:13700-13735）。训练库早有指纹幂等（training-library-service.ts:56-63、116-119），知识资产没抄这道工序。
G3team_id='all' 孤儿资料谁都看不到schema 默认 'all'（schema.mysql.sql:434），而 canSeeKnowledgeAsset（server.ts:1713-1719）与 collectKnowledgeAssets（resource-hub.ts:197-202）都要求 teamId===actor.teamId 且平台身份被 isPlatformIdentity 排除 → 兜底值反而双处不可见。此前实测 4 条里 3 条不可见。
G4无质量检查、无归档、无版本线性化status 只有 draft/review/published（types.ts:1006）；过期版本只能物理删除（DELETE，server.ts:13826）；标题=文件名、无说明、无标签、无链接的资料与好资料在推荐里同权。

B · 检索闸断点

编号问题证据与影响
G5hasExternalLink 算出来了但从不参与召回resource-hub.ts:215 算出该字段，scoreHubResources 全程不读 → 无链接的 legacy 资料照样占推荐位；用户点「复制链接」必得 409 no_link（server.ts:19993）。扩展只能把按钮藏掉（resources.js:165），候选位已被浪费。
G6400 行静默截断MAX_SCAN_PER_SOURCE=400（resource-hub.ts:31、330-333），第 401 份起不进候选集，界面与 warnings 均无提示——资料越多，「新资料反而推不到」越明显。
G7词法分按「全部查询词 idf 之和」归一，长会话无区分度resource-hub.ts:433 取查询词全量 idf 之和作分母，:457 归一。长会话查询词 20 个时，命中 1 个高权词的资料 lexical≈0.05，挤在淘汰阈值 0.01 附近——此前实测曝光均分 0.041（区间 0.017–0.10），候选之间拉不开。
G8dismissed 从不参与排序，UI 承诺是空的扩展「没帮助」按钮提示「下次会排后面」（agent.js:912），但打分只读 sentCounts（resource-hub.ts:482-487）。反向风险：customerResourceKeys 把 revealed 也算进「该客户此前收到过同类资料」+0.5（:463-467、:751-763），同会话内已看过的资料反而加权；且文案说「收到过」与实际「查看过」不符。
G9向量通道空转saveEmbeddings 无调用方 → resource_embeddings 永远空表；recommend 的向量分支（server.ts:19922-19945）只有调用方传 queryVector 且仓库有向量才生效，而两端都不满足 → 权重表里的 vector 0.12 是死重，「语义」实际只剩业务词典展开。

C · 反馈闸断点

编号问题证据与影响
G10accepted 事件没有任何界面产生，采纳率恒 0扩展只发 dismissed / sent（agent.js:898-921）；crm.js:270 的 accepted 只是兜底分支；CRM 侧无资源交互界面 → adoptionRate = accepted/max(1,revealed)（server.ts:20065）结构上永远是 0%，报表「采纳率」一列是死列，扩展 options 卡（options.js:263）照显示。
G11文件中心「打开资料」不记埋点POST /api/knowledge/assets/:id/access（server.ts:13795-13824）只加 accessCount，不写 resource_retrieval_events → 业务员在 CRM 内的查看完全不进报表，exposed/revealed 只反映扩展侧行为。
G12反馈不回流排序eventStats 只喂报表（server.ts:20047），scoreHubResources 不用采纳率/发送率 → 「曝光 20 次 0 采纳」的资料不会被降权，下次照样推。
G13训练库：导入即启用、口径全量注入、命中计数半条链① importFromProfile 直接建 enabled 条目（training-library-service.ts:188-205），档案样本（含时间戳/附件名/截断半句）无人工确认就进提示词；② resolve() 的 snippet/policy 按列表顺序取前 6/10，零相关性过滤（:223-224）——污染最快入口；③ recordHits 只有自动回复一个调用点，推荐回复路径不记，hit_count 永远偏低；④ 报表只有扩展 options 一张小卡，CRM 内无视图。
G14埋点表只增不减：90 天保留期是空头支票pruneEvents（resource-hub.ts:834）实现了但全项目无调用方，没有任何定时任务触发——resource_retrieval_events 无限增长，eventStats 的全表 GROUP BY 会越来越慢，反馈回流（P3-2）还没做就背着一个膨胀的表。server.ts 已有定时器先例（reminderRuleSchedulerTimer:26077、aiEngineRecoveryTimer:7858），照抄即可。
共同根因：这套系统的「写侧」（录入、埋点、接口）建得相当完整，但「读侧的三道加工」——入库校验、召回过滤、反馈回流——基本空缺。表现就是用户看到的「资料很多、推荐很糊、说不清哪份有用」。

§4方案总设计：三闸两池

不是重写，是补齐三道加工。每道闸都对应 §3 的一组断点，每个池都有明确的进入条件与权重。

图 2 · 三闸两池总设计。闸二内含两池分层；底部虚线是治理回流（让闭环真正转起来）

4.1 两池的进入条件与权重（不设硬上限）

池进入条件权重说明
核心池published 且 verified=1（发布/编辑时管理端勾选「已校订」）score × 1.0人工校订过 = 团队认可的口径，理应排前面
长尾池published 且未校订score × 0.5仍然可被推荐（精确命中时），只是排在核心池之后
为什么不再设「上限 200」这类红线：MAX_SCAN_PER_SOURCE=400 已经证明，硬上限的失败方式是静默截断——第 201 份资料消失且无人知道。本方案用「权重 + 反馈淘汰」代替硬上限：低采纳资料被降权（G12），过期资料被归档（G4），死条目进清理清单（G13）——让该沉下去的自然沉下去，不设看不见的天花板。

4.2 与既有设计文档的关系

docs/RESOURCE-HUB-DESIGN.md 的「外链唯一出口」「埋点旁路」「memory 档可测」等纪律全部保留并延伸；docs/RESOURCE-FEEDBACK-REPORT-DESIGN.md 的报表口径（分母都是 revealed）保留，本方案补上它缺的「accepted 从哪来」（G10）与「回流排序」（G12）。docs/FILE-CENTER-DEVELOPMENT.md 的百度网盘边界（只存链接、不抓取）不变。

§13三轮自审记录

三轮都对着真实代码审，不是措辞润色。每轮记录审了什么、发现什么、改了什么。共修订 20 处。

第一轮 · 数据模型与接口一致性方法：逐条把方案里的表字段/接口/迁移位置与源码对照
F1-1词表原本设计成全局表 —— 与「团队隔离」铁律冲突：A 团队的「认证资料」类目不该出现在 B 团队下拉里。修订：词表改团队级（team_id 列 + UNIQUE(team_id,type,normalized)），迁移时以团队为单位种子化。
F1-2孤儿修复原本写「统一改成 owner 的团队」 —— owner 被删后查不到团队，这条 UPDATE 会把 team_id 写成 NULL，资料照样不可见，且无人知道。修订：查得到团队的才修；查不到的进「孤儿清单」（治理 Tab 可见、可手改），repair 函数返回两类计数。
F1-3verified 原本默认 true —— 迁移后存量资料全部变成核心池，两池分层当场失效。修订：DEFAULT 0，核心池只认「迁移后人工勾选过」的资料。
F1-4词表强制校验原本对 PATCH 也硬拦 —— 老资料一编辑就被 400 挡住，用户以为系统坏了。修订：硬拦只对 POST/PATCH 的新值生效，且提供「建议新类目」出口；存量读取链路完全不受影响。
F1-5「新增 status=archived」原本没查筛选与文案链路 —— 实测 knowledgeStatusText（prototype-api.ts:24425-24427）对未知状态会 fallthrough 成「草稿」，archived 资料会显示成草稿；前端状态下拉也没有该选项。修订：补查三处：knowledgeStatusText 加 archived 分支、状态下拉加「已归档」、详情页显示归档信息；collect 的 status==="published" 天然兼容（无需改）。
F1-6迁移位置核实 —— 确认 CRM 用 ensureXxxSchema 顺序调用（mysql-store.ts:2229-2245）+ ensureColumn/widenColumn/ensureIndex 可复用；插件迁移版本化且 sqlite/mysql 双份（mysql-migrate.ts v15 为最新，下一版 v16）。方案中的迁移写法与现有基建完全对齐，无需新造机制。
第二轮 · 功能闭环完整性方法：沿四个闭环各走一遍「触发→动作→记录→生效→可见」，专找断头路
F2-1accepted 埋点原本只写了「复制链接成功」 —— 「看正文」（inline）分支漏了：知识条目没有外链，用户看完正文也是一种采纳，否则 knowledge 源的采纳率永远是 0。修订：revealAndCopy 的 inline 分支同样发 accepted。
F2-2CRM 内「打开资料」原本没进埋点 —— 报表只看扩展侧行为，业务员在 CRM 的查看完全不计入，revealed 口径残缺。修订：access 接口补一条 revealed 埋点（旁路写）。
F2-3训练库候选池原本没定义存量处置 —— 若把存量 45 条一并标 candidate，自动回复当晚就没语料可用。修订：迁移 DEFAULT 'active'，只有 importFromProfile 新建的进候选池；候选条目在训练页可搜索（默认筛选 active，切「全部」可见候选），不是看不见的死数据。
F2-4「合并词条」原本只有想法没有接口 —— 治理闭环里「维护动作」缺了抓手。修订：补 POST /api/knowledge/vocabulary/merge（批量改资料 + 停用旧词条 + 返回影响数），前端 confirmAction 列后果。
F2-5recordHits 原本只写了「推荐回复路径」一句 —— 顺着调用链全查一遍，实际情况更细：CRM auto-chat-service.ts:712 有（自动回复通道）；插件侧 handleInbound（自动回复，auto-chat-service.ts:706-713）有，但 compose()（推荐回复 + 资料，被 /v1/auto-chat/suggest 调用，app.ts:1222）在 :537 loadLibrary 之后没有 recordHits——正是用户天天点的面板路径；插件 /v1/resources/search（面板初值目录检索）是纯目录，不该记 exposed。修订：三条路径的记/不记及理由写进 §8.1，compose 的 recordHits 与 loadLibrary 同款 fire-and-forget。
F2-6dismissed 降权原本没防「刷新吞点击」 —— 扩展既有教训：自动刷新可能在用户点下去那一刻返回。降权走「同会话 dismissedKeys」而非硬过滤，刷新不清 dismissed（agent.js:676 已有此纪律），两者不冲突。修订：确认降权为软权重，不回列表硬删。
F2-7报表视图权限核实 —— /api/agent/resources/stats 是 requireAuth + teamId 口径，CRM 新视图直接复用即可，不需要新权限点；未登录/空团队由前端出引导文案，不出全 0 假数据（沿用 options.js:243 纪律）。
F2-8治理闭环漏了「表本身的生命周期」 —— 原本只盯着资料的生命周期，没查埋点表的：pruneEvents 实现了但无调用方（resource-hub.ts:834，全项目零调用），事件表无限增长，P3 的反馈回流还没做就先背一个膨胀的表。修订：新增 G14 与 P0-0-6（每日 prune 定时器，照 reminderRuleSchedulerTimer:26077 先例），把「保留期」从注释变成真跑的东西。
第三轮 · 可测性与落地可行性方法：把每条验收标准改写成「能跑的命令/能断言的数字」，查与铁律的冲突
F3-1lexical 修复原本没有回滚手段 —— 它是核心排序变更，直接改行为等于把推荐体感当赌注。修订：加 RESOURCE_LEXICAL_V2 开关，默认关；回测脚本先对比新旧 Top5 重合度与分差；断言「20 词长查询下 Top1-Top5 分差 ≥ 0.05」；观察一个周期再默认开。回滚 = 关环境变量。
F3-2向量 backfill 原本排在 P1 —— 一查发现 saveEmbeddings 全项目无调用方，且 embedding 调用需要 AI 网关凭据，落实前无法验收。修订：降级为 P3 决策项：先关闭假通道（useVector 缺省 false + 注释标注 0.12 权重暂不生效），凭据通道落实后再评估 backfill。不留「看起来能用」的死代码。
F3-3验收标准原本有「效果更好」类不可测表述 —— 全部改写为数字断言（分差 ≥0.05、降权 ×0.5、候选 100% 可达、种子数 = distinct 数、20 条批量确认等），并落到具体测试文件（§11）。
F3-4前端改造原本没查规范冲突 —— 新视图若自建字号/圆角，会重演「78 条规则各写各的」。修订：明确新统计块选择器补进 head-text-refine 分组、新控件补进 input-refine 分组，样式块都在 body 末尾；截图取景用 CDP 读 closest('.view').id 判类。
F3-5双库顺序与铁律对齐核实 —— 每个 P1 事项都标注「改码 → db:migrate:dev → db:migrate:personal → goodjob-db-parity.sh」；禁用 app:personal、禁连 goodjob_crm*/goodjob_web；测试档用内存/sqlite（CRM_STORE=memory 与 -test.ts 已有先例）。
F3-6「P0 不改表」承诺核实 —— 逐项核对：0-1 是数据修复（repair 函数，不动结构）、0-2/0-3 纯计算、0-4/0-5 是埋点、0-6 是定时器。确认 P0 六项均不触发迁移，当天可验的说法成立。
F3-7「资源中心视图」原被写成「改造」，实际是从零新建 —— grep 证实 CRM 前端对 /api/agent/resources 零消费（prototype-api.ts 无任何调用），目录/报表/治理三个 Tab 全是新代码；另核实插件 ResourceHubClient.list()（crm-resources.ts:169-188）现传 5 个参数，CRM 侧加可选 reachable 向后兼容、插件搜索路径显式传 1。修订：P2-2 按「新建视图」排期，并在 §7.2 注明这是 CRM 内首次消费 reveal 出口（权限口径与扩展一致，团队隔离天然成立）。
F3-8eventStats 缓存原排在 P3，但 P2 的治理看数先消费它 —— 治理 Tab 每次打开是全表 GROUP BY，P3 才加缓存等于中间好几个版本都在裸跑。修订：缓存摘要（repository 层、team 维度、60s）提前到 P2-2 与治理端点一起落地，P3-2 的反馈回流直接复用同一缓存，不写第二份。
