2低于 9 分的项：具体改了什么

A · 试问屏按错误的契约渲染 5.5 → 9.5 正确性

插件 resolve() 返回的 hits 是 TrainingLibraryMatch（{entry, similarity, matched, matchedTerms}），而 citations 才是「可展开的出处」。修前前端把两者都当出处渲染并相加，后果是：

  • 每条命中的标题 / 摘要 / 命中词全部取到 undefined → 渲染成空壳（此前只在界面上补了兜底文案，是治了症状没治根因）；
  • 同一条问答既在 hits 又在 citations → 行数翻倍，验收时读到的「命中 10 条」其实是重复计数；
  • blocked 字段并不存在 → 「插件侧会拦下这次自动回复」永远不会显示。

修法：正文出处以 citations 为唯一来源（四类合一、按条目去重），hits 只用来补问答特有的相似度与「含词典等价命中」；verdict 作为护栏判决直接展示；forbidden 单独红色块回答「哪句被拦、为什么」；按问答对 / 口径 / 政策分组。

现场证据：「What is your MOQ?」→ 渲染 7 行、标题去重后 7 行（问答·2 + 政策·5，相加即 9 行的重复已消失）；护栏判决「命中 2 条问答（最高相似度 0.44，含词典等价命中）；引用 0 条口径；5 条政策」。

B · 批次候选计数少两态，界面数字恒为 0 后端 5.5 → 9.5 契约

摘要那行「待确认 / 已确认 / 已发布 / 已丢弃」按状态数对齐，但 countCandidatesByRun 的 SQL 只 SUM(pending) 与 SUM(published)。界面上「已确认」永远显示 0，用户会以为自己的确认没生效。

现场证据：对一条候选执行「编辑 → 保存并确认」后，摘要从「待确认 7 · 已确认 0」变成「待确认 6 · 已确认 1」。修前这一步只会显示「已确认 0」。

自检补了一条跨文件断言：countCandidatesByRun 必须四态齐全，删掉任一态即变红。

C · 轮询失败会刷屏，截断与空池沉默 6.0 → 9.0 降级可见

  • 轮询刷屏：自动刷新每 3 秒走一次「批次列表 + 批次详情 + 候选」，两条失败路径都无条件 toast。后端抖一下就会刷满界面。现改为静默计数，连续 3 次失败即停自动刷新，并在批次列表顶部说明「自动刷新已停（连续 N 次读取失败）：点右上角刷新重试」。
  • 静默截断：批次详情最多带 100 条候选，超出部分此前毫无提示（与项目历史上 MAX_SCAN_PER_SOURCE 静默截断是同一类问题）。现用数据库计数与已装条数比对，超出即明说「本批共 N 条候选，界面只装了前 100 条」。
  • 空池 / 部分完成：§9 要求「本批未发现新条目」是提示不是报错。现按真实 stats 给出成因与下一步：N 条与库里重复 → 换一份更具体的资料；把同一份资料重训一次补齐未提炼的段落（已进库的不会重复）。
现场证据：重复提交同一批资料 → 批次卡显示「语料 2 段 · 入池 0 条 · 重复 5」并给出琥珀色建议行；这正是 §9#8 的幂等路径，界面不再只有一行干巴巴的 0。

D · 人工确认闸缺「改」这一环 7.5 → 9.0 功能

后端 reviewCandidates 早就支持 edits（改内容还会重算指纹，避免「改完再训同一份资料」被误判重复），但前端没有任何编辑入口 —— 提炼出的答案只要不合口径，候选就只剩「原样发布」或「丢弃」两条路。现补行内编辑：问法 / 答案可改，「保存并确认」把编辑与确认合成一个动作（改了不确认等于没改）。

现场证据：进编辑态自动聚焦答案框；改完点「取消」→ 原文完整还原（cancelRestored: true）；点「保存并确认」→ 新答案落库并在界面显示，筛选自动切到「已确认」。

E · 一次只能训一份资料 + 出处不可点 8.0 → 9.0 功能

  • 多份资料：本地 txt / md 改多选（后端 text.items 上限 50 条），暂存清单可逐条移除；提交后清单清空并把视图切到这一批。
  • 出处可点：候选出处渲染成链接，点击调 openKnowledgeAsset 打开对应文件中心资料（此前 CSS 里已有 .kb-candidate-meta a，但从未渲染过链接 —— 死代码）。
  • 顺手修掉的耦合：关联资料此前会被同时塞进 files.assetIds，而后端把该路径当内容源，资料说明（实测只有 7 个字）会被当作一份语料喂进提炼。现只走 text.items[].assetId（资产元数据照样解析，出处照样回指），并加了回归断言禁止再次出现。
现场证据：一次提交两份文件 → 批次「语料 2 段 · 入池 7 条」，候选出处分别为「LED参数手册V3 §1」与「付款与单证口径 §2」——每份文件各自带出处。暂存两份时「关联文件中心资料」自动禁用并说明原因（无法指向具体哪一份）。

F · 「必须会红」的自检质量 7.5 → 9.0 可验证性

本轮重点不是加断言，而是加会红的断言。三次自查发现第一版断言有漏洞：

  • 「试问必须展示护栏判决」写成「源码里出现过 probe.verdict」→ 把渲染那一行删掉照样通过（守卫条件 if (probe.message && !probe.verdict) 里也有它）。改为必须命中 escapeHtml(probe.verdict) 那一行。
  • 「轮询失败必须静默」写成「存在一处」→ 只改另一处仍通过。改为断言计数 ≥ 2（轮询与批次加载是两条独立路径）。
  • 同类问题还出现在「答案输入框必须存在」（渲染处与聚焦选择器是两件事）与「暂存清单必须能清空」（提交后清空 / 手动清空）。
13 个破坏点全部实测变红并还原：试问不渲染护栏判决 / 不渲染被拦场景 / 出处不分组 / 确认不提交 edits / 本地文件去掉 multiple / 提交不带多份 items / 计数缺 approved / 伪造 blocked 字段 / 截断不提示 / 轮询失败改弹 toast / 连续失败不停轮询 / 出处不可点 / 暂存不能清空。

5仍未达 9 的项（附理由，不硬凑）

  • 试问屏「拟用回复」未做（§7.2 屏 3 提到）。闭环②的三条判据（同源检索 / citations 可回指 / 撞护栏说明哪句被拦）都不要求出稿；而插件侧没有「只出稿不落档」的读口，真出稿要走完整 compose()（含资源推荐，秒级到十秒级），与「试问」按钮的语义不匹配。决定：延后到 P3 与引用校验一起做，届时出稿与「引用 id 必须 ⊆ citations」的校验天然同源。
  • 候选筛选缺「按来源」。P1 只有文件源，加了也是死筛选项，与 P2 会话源一起补。
  • 跨批次候选分页（游标）未接前端。当前按批次装前 100 条 + 本地筛选，已在界面明示截断；跨批次视图属 P2。
  • 自检是「源码活代码行」级，不是「行为级」。它能抓住「接线被拆掉 / 选择器拼错 / 契约字段缺失」，抓不住「渲染出来是空的」。行为级断言需要页面级测试框架，属独立投入；本轮的补偿是全部关键路径都做了浏览器现场验收并留存数字。
