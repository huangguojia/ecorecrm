GoodJob CRM · 知识库训练方案

知识库训练：把散落的语料，变成可追溯的推荐能力

目标：训练一次 → 插件立刻能用（自动回复 + 推荐回复），每条推荐都点得开来源。 一句话方案：不训模型，训语料——CRM 做「训练工作台」（采集 → CLI 提炼 → 人工闸门 → 发布 → 回流）， 插件做「运行端」（检索 → CLI 精选 → 回引校验 → 出稿带引用）。 检索按你的偏好走 CLI 优先：CLI 负责"从候选里挑并按 id 回引"，不负责"凭空给事实"。

先把口径对齐，避免做错方向。 「训练」在本项目里不是微调模型，而是语料生产流水线：把历史会话、文件中心资料、人工口径， 炼成结构化的 qa / snippet / policy / forbidden 条目，推进插件的训练库（training_library_entries）， 由它供给自动回复与推荐回复。这是上一份文档体检（doc-management-review.html）定下的方向， 本次是把它的执行层设计完整——特别是你这次新增的三条要求：CLI 去查、训练要简易、来源要看得见。

1.1 四个断点（本次要修的）

① 生产端错位

训练库长在插件控制台（3100），你日常看的是 CRM。CRM 里既看不到库、也不能审核—— 「训练」这件事没有工作台，只能靠对话里推。

② 准入太松 + 有污染口

45 条里没有一条是人工逐条确认的（全是档案批量导入）；selectSnippets 在"全不相关"时 仍硬塞 priority 前 6 条；policy 超限只 warning 不截断——无关内容照样进提示词。

③ 反馈断链

命中计数只覆盖 qa 一类（compose / generateReply 两处），snippet / policy / forbidden 命中永不计数； forbiddenHits() 是死代码；curation-engine.ts 定义了但没接线。 没有数据，就答不出"哪条有用"。

④ 来源只到"标签"粒度（你这次最直接的痛点）。 现在界面上只能看到「训练库」这个小徽章 + 一句依据文案，点不开、看不到是哪一条、来自哪份文件、哪一句原文。 等于"我说我有依据"，但没法证明。要让它成为证明，来源必须做成三层可展开的证据链， 而不是一个标签。

2主流做法调研：五条能用的结论

调研了 2026 年的公开实践（RAG 工程、会话挖 FAQ、评测口径），只保留与本项目相关的五条。

主流结论证据/口径本项目怎么用
① 不训模型，走检索 微调的代价是"更新要重训（小时～天）、成本高、引用来源难追溯"；检索是"改一份文档，秒级生效、能指回具体片段"。结论：绝大多数业务问答场景检索是正解。 维持旧结论：训语料不训权重。这也是本项目唯一可行的路（模型走外部网关，没有微调通道）。
② 引用可追溯靠「混合检索 + 重排」打底 企业级实测：混合检索（稀疏 BM25 + 稠密向量）比"只向量"在 recall@10 上 +11 个点，加重排再 +6 个点；只向量时，含产品型号/SKU 的查询会大面积失败。 词法（现成的 idf 加权）当地基，向量只做可选精排。绝不把向量当唯一召回通道——现有系统已经是这个姿态。
③ 引用必须先"能被指认"，再谈好看 结构感知分块（按标题/段落切，512 token / 64 重叠）+ 稳定 chunk id + 页码/段落锚点；"引用的片段要能支撑那句话"。引用准确率在未做归因训练时只有 65–70%，所以必须校验。 每条训练条目与每份资料都要有 source_ref（条目 id / 文件 id + 段落锚点 / 会话 key + 消息 id）， 生成时回引、发布时校验。
④ "只依据资料回答，否则拒答"是幻觉降幅最大的一招 同一套系统实测：不加约束的幻觉率 18.4%；混合检索降到 6.2%；加上"引用或弃答"（cite-or-abstain）契约后降到 3.1%——近 6 倍，且这一项比换模型有效得多。 把"必须回引 + 引不到就转人工"写成硬契约，而不只是提示词里的软提醒。
⑤ 从历史会话挖 FAQ，靠"机器做减法 + 人做加法" 行业落地（如支付宝客服知识生产）：机器从会话抽取 QA → 人工采纳，采纳率约 65%，单条生产时间从 10 分钟降到 2 分钟；另一类工具的做法是每条 QA 都附上来源会话片段、按 CSAT/客服质量过滤后才入库，2–4 周同步一次。 直接照搬这套节奏：CLI 批量抽候选（含出处与理由）→ 批量确认 → 带血缘发布；把"每条 2 分钟"作为体验目标。
调研里最该警惕的三个坑（我们已有其中两个的影子）。 ① "什么都入库"——营销话术、过期文档会直接拉低准确率（对应我们的"45 条全量导入、0 条人工"）； ② 分块过碎或过大——100 字丢上下文、2000 字稀释检索（对应我们目前图文混排的资料没有段落锚点）； ③ 跳过评测——没有 golden set 就没法知道改动是变好还是变坏（对应我们目前"训练完无法自证"）。

3方案总览：一条流水线，两道闸门，一张成绩单

STEP 1采集会话库 + 文件中心 + 手工口径，三源
STEP 2CLI 提炼抽问答对/口径片段/政策/禁用语，附出处与理由
STEP 3候选池pending，不进提示词
STEP 4确认闸20 条/屏批量确认；白名单可自动
STEP 5发布推插件训练库 → active，记血缘
STEP 6检索词法召回 → CLI 精选 → 回引校验
STEP 7回流采纳/改写/丢弃 → 加权或退役

3.3 CLI 提炼：一次训练只花 3–5 次调用

复用 CRM 里已经落地的 CLI 通道（backend/src/cli-ai.ts，就是跟进补全那条链路：本机 CLI 优先、 失败退 CRM 配置的模型、都没有则如实降级）。不是每条候选一次调用，而是按批：

  • 确定性预处理（不调模型）：按内容指纹去重、剔除时间戳/附件名/系统短语/纯表情、标注语言、抽候选标签。
  • CLI 批量提炼：一轮 20 段语料 → 一次调用 → 返回候选数组（每 20 段 1 次，训练 100 段 ≈ 5 次调用）。
  • 去重判定：CLI 同时收到"现有库条目的问法清单"，对每条候选判 new / duplicate / update（对齐主流做法第 ⑤ 条）。
  • 每条候选必须带：kind / question / answer / tags / languages / source_ref / rationale（为什么值得进库）/ confidence。

3.4 两道闸门：入库闸 + 发布闸

入库闸（候选池）

  • 机器产出的一切先落 pending，不进提示词（沿用现有状态机）
  • 无 source_ref 的候选永远停在 pending（这是"来源即门禁"的落点）
  • 同一指纹只留一条；update 类候选指向既有条目，走"改写"而不是"新增"

发布闸（推给插件）

  • 默认：人工批量确认后发布（20 条/屏，预勾选高置信）
  • 白名单自动：答案来自已校订文件 + 置信 ≥0.9 + 不含价格/交期承诺 → 允许"一键放行"
  • 每次发布记批次血缘：候选 → 训练条目 id，支持按批次撤回

3.6 检索按你的偏好走 CLI：CLI 有选择权，没有编造权

检索链路（一次推荐回复）

客户来文 → 词法+结构化召回（宽，12–20 条候选，纯确定性） → CLI 精选（窄，只能从候选里挑 + 说明为什么 + 合并同族） → 回引校验（引用的 id 必须在给定 citations 内） → 出稿带引用

CLI 能做

挑选、排序、合并同义、给出"为什么选它"、把候选内容改写成客户语气

CLI 不能做

引入候选之外的任何事实；引用不存在的条目；给出价格/交期承诺

CLI 不可用时

词法结果直接出（不空等、不报错）；同问法 5 分钟内复用上次选择（缓存）

5三轮自我辩论

第 1 轮语料该从「会话」挖，还是从「文件」挖？
正方 · 会话派

会话是唯一能解决"客户不按你的词表说话"的语料源。文件里写的是"IP67 防护等级"， 客户问的是"这玩意儿能淋雨吗"——只有会话里有这种问法。而且会话自带频次，天然能筛出高频问题。

  • 真实问法 → 检索命中率提升，这是词法检索最缺的东西。
  • 中英混问、口语、缩写的分布只有会话里有。
  • 历史会话量远大于文件量，训练"有量"。
反方 · 文件派

会话脏，而且危险：时间戳、表情、"test test 2"、议价过程、以及我方随口给的承诺。 一条错误答案进了训练库，会被反复引用，且引用时还挂着"有依据"的招牌——比没有更糟。

  • 会话里我方答复的质量参差，没人保证它是标准口径。
  • 价格/交期这类内容一旦被固化成"标准答案"，等于给销售上了锁。
  • 文件是校订过、有版本、可追溯的；会话不是。
裁决

按角色分工，不是二选一：会话贡献「问法」，文件贡献「答法」。

落到实现上就是三条硬规则： ① 候选条目的 question 可以来自会话，answer 必须标出来源类型 （file / manual / conversation）； ② answer 来源是 conversation 的，一律不能自动放行，必须人工确认（它是"我们当时这么答的"，不是"我们标准这么答"）； ③ 会话里抽出的问题，若在文件里找不到答案，进候选池但标记为"知识缺口"—— 这恰好是调研里说的"补 15 条 FAQ 让准确率从 70% 到 85%"的那个补法。

为什么重要：如果按"会话全收"，一个月内库就会变成聊天记录堆， 而"来源证明"会把一堆不可信的东西标成有依据——可信度比覆盖面更难挣回来。

第 2 轮「用 CLI 去查」——CLI 该做主检索，还是只做精排？
正方 · CLI 主检索派（你的倾向）

词法匹配的死穴就是"意思到了、词没到"。CLI 能把整段来文读懂，还能顺带给出"为什么选它"， 这正是"来源证明"要的素材。而且本机 CLI 已经在跑（资源复排、跟进补全），通道是通的。

  • 跨语言场景（中英混问）靠词法几乎必漏，CLI 能救。
  • 一个话题有 8 种问法时，CLI 能合并成一条，而不是占满 5 个名额。
  • "为什么推荐它"这句人话，只有模型能给，规则给不了。
反方 · 确定性优先派

检索是高频路径，把主检索放在 CLI 上等于每次都赌一次：CLI 进程能不能起、登录态有没有过期、 网络通不通、这次会不会返回跟上次不一样的答案。而且模型有臆造倾向——万一它"挑"了一条不存在的条目呢？

  • 延迟：一次 CLI 出稿 10 秒起步，资源复排给的超时是 60 秒。用户在跟客户聊天，等不起。
  • 不确定性：同样的问法两次结果不同，故障无法复现，排查成本高。
  • 臆造：模型天生倾向于"给个看起来对的答案"，而不是"承认没有"。
裁决

CLI 有"最终选择权"，但没有"编造权"——把它关在候选集里。五条约束同时成立：

  • ① 召回用规则，选择用 CLI。词法 + 结构化先召回 12–20 条候选（确定性、微秒级）；候选 ≥2 条或分数接近时才叫 CLI。
  • ② CLI 只能从候选里挑，且必须回引 id。挑的 id 不在候选集 → 直接丢弃并计数（沿用资源复排已有的"防臆造"规则，不新造轮子）。
  • ③ 引不到就弃答。生成阶段要求逐句回引 [[src:id]]，代码校验；引不到 → 草稿标"依据不足，建议人工"，不硬编。
  • ④ CLI 不可用就用词法结果，不空等。超时（建议 8 秒）即降级；同问法 5 分钟内复用上次选择。
  • ⑤ 提示词里写死边界："你只做选择、排序、合并与措辞；不得引入候选之外的事实"。

这条同时也是对"你倾向 CLI"的正面回应：推荐结果确实由 CLI 决定（选哪些、怎么排、怎么说）， 但它的素材全部来自可追溯的库，出了问题能指回具体条目——CLI 是抓药的人，不是药本身。

第 3 轮「显示来源」只是界面装饰，还是应该当准入闸门？
正方 · 装饰论（要简易）

来源是给人看的，看着放心就行。要求每条都有出处，等于把大部分候选挡在门外： 会话里挖出来的问法哪来的出处？手工补的口径哪来的文件？训练就没量了，没量谈什么效果。 而且你说了要"简易友好"——上来就让填出处，谁还愿意训。

反方 · 门禁论

不可追溯的知识等于凭记忆回答，只是换了个地方记。调研里最大的幻觉降幅（18.4% → 3.1%）来自 "引用或弃答"的硬契约，不是界面上多了个徽章。如果来源只挂在 UI 上、发布时不校验， 那"有依据"就是文案，出事时你依然指不出是哪条规矩错了。

裁决

来源是硬门槛，但门槛后面留了快速通道——简易性不靠放松标准，靠减少点击。

  • 硬门槛：无 source_ref 的候选永远停在 pending，不进提示词。没有例外。 但"出处"可以是三种之一：文件段落 / 会话片段 / 人工口径（人工口径的出处就是"谁在什么时候定的"）。
  • 快速通道：出处是文件 + 置信 ≥0.9 + 不含价格交期 → 预勾选、可一键放行； 其余人工扫一眼。屏幕一次 20 条、键盘 J/K/空格/Enter，目标 2 分钟过完一屏。
  • 发布时校验，而不是生成时才校验：入库那一刻就把出处写死，之后任何一次生成都能直接引用， 不需要临时去找依据。
  • 引用准确率要监控：调研指出未做归因训练时引用准确率只有 65–70%， 所以"引用的条目是否真的支撑那句话"要作为成绩单的一项，持续看。

三轮辩论的共同落点：库里每一条都能指回出处，界面上每一次推荐都能点开出处， 指不出来的一律不进库、不出稿。这就是"显示证明来源"从装饰变成能力的全部含义。

7需要你定夺的三件事

① 价格/交期这类口径，进不进训练库？ 进：客户问起时能给出准确边界，销售口径统一；风险：一旦写错就是全体销售一起错，且会被"有依据"背书。 我的建议：进库，但标为"仅供人工参考、不参与自动生成"（检索层对它单独降权/不进入可引用集）。

② 训练频率与量级？手动按需 / 每周一次 / 每次会话结束自动增量。 我的建议：默认手动 + 每周提醒，且只在"新增会话 ≥ 20 段"时才提示，避免天天打扰。

③ 发布默认动作？全部人工确认 / 高置信自动放行。 我的建议：高置信 + 出处是文件 + 不含商务承诺 → 自动放行（可撤回），其余人工确认。

8与既有铁律的一致性检查

既有约束本方案是否冲突说明
绝不把客户原文写进 CRM 库不冲突候选条目只存"整理后的问答对"；会话出处用 source_ref（会话 key + 消息 id）指回，原文仍只在插件会话库，按需拉取
只读绝不发送不冲突整个链路不向 WhatsApp 发任何消息；自动回复维持"草稿，人工发"
匹配不上就不猜同源原则检索同样落地为"引不到出处就不给稿"
不做模型训练不冲突本方案是语料生产，无权重变更
提示词预算 ≈8000 token不冲突分层与合并是为了在同样预算里放更有用的内容，不是扩容
