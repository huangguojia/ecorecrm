# ECORECRM 性能审计与写路径优化（2026-11-13）

> 触发：用户询问「CPU / 内存占用是多少、有没有像 GoodJobCRM 那样优化、多余的读取有没有去掉」。
> 本文记录实测数据、已具备的优化、本次新增改动与遗留项。

## 一、实测占用（生产 `https://www.ecoreglobalcrm.com`，`ecorecrm-1.1.10`）

| 容器 | 内存 | 占限额 | CPU |
|---|---|---|---|
| `goodjobcrm-backend-1` | **157.9 MiB** | 24.67%（640 MiB） | 0.00% |
| `goodjobcrm-mysql-1` | 312.9 MiB | 40.74%（768 MiB） | 0.15% |
| `goodjobcrm-communication-1` | 15.86 MiB | 4.13%（384 MiB） | 0.00% |
| `goodjobcrm-gateway-1` | 5.91 MiB | 6.16%（96 MiB） | 0.00% |

**空闲 60 秒 MySQL 仅执行 11 条 SQL（≈0 QPS）**。

需要说明的是，这个数字一部分来自优化，一部分来自**生产库接近空库**（采样时 4 客户 / 1 单据 / 2 跟进 / 22 日志）。
业务数据长起来后，真正的风险在第三节的写路径。

### 采集方法（受环境限制）

- 本机 `ps` / `top` 被沙箱硬性拦截（含 `dangerouslyDisableSandbox`），无法取本地进程占用 → 改用生产 `docker stats`。
- 生产 MySQL `performance_schema = OFF`，`events_statements_summary_by_digest` 为空，读不到语句摘要 → 改用 `SHOW GLOBAL STATUS` 做增量采样。
- 生产 cgroup v2 路径（`/sys/fs/cgroup/memory.peak`）在容器内不可见，内存峰值取不到。

## 二、已经具备的优化（读路径）

| 优化 | 作用 |
|---|---|
| `validationView()` | 校验只读改浅拷贝视图，不再 `structuredClone` 整库（历史上轮询每几秒复制全库一次） |
| `persistenceSnapshot()` | 落库快照只复制数组外壳、元素共享引用，原来每次 `persist()` 都深拷贝整库 |
| `createReloadGuard(maxAgeMs)` | 轮询可声明「数据这么新就够用」，窗口内复用上次重载结果 |
| `ECORE_HIDDEN_MODULE_WORKERS`（默认 false） | 获客 / Agent / 邮件中心 / 培训 / 提醒规则的**后台线程整个不启动**（原 agent runner 1 秒、superSearch 5 秒、scheduler 15 秒轮询）。生产日志已确认打印该行 |
| 实例锁探活 | 去掉每 15 秒一条 `SELECT IS_USED_LOCK()`，改 `COM_PING` |
| GET 走内存镜像 | 客户 / 供应商 / 内部消息 / 未读数全部内存直读，零 SQL |
| 前端轮询守卫 | 仪表盘 30 s 且必须「已登录 + 页面可见 + 当前在仪表盘视图」；角标 5 s、消息 30 s 均限可见；WhatsApp 12 s |

结论：**读路径确实做过优化，且比 GoodJob 更彻底**（GoodJob 只是不轮询，ECORECRM 是连 worker 都不启动）。

## 三、本次发现并修复的问题

### 3.1 写路径：一次写 = 93 张表全量重写（已缓解）

`persistAll()` 里 **93 处 `replaceRows`**，实现是：

```sql
DELETE FROM <table>;            -- 整表清空
INSERT INTO <table> VALUES ...; -- 全量重插（每 500 行一批）
```

只有 `users` 用 `upsertRows`。**无 debounce / throttle**。

实测（本地库 12 个客户）：改一条客户备注 = **153 条 SQL / 177 ms**。
被重写的表含只增不减的 `customer_activities`、`lead_activities`、`whatsapp_messages`、
`wecom_messages`、`trade_documents`、`agent_run_events`、`outbound_email_logs`。

对照 GoodJob：同样是 93 处 `replaceRows`、同样无节流；ECORECRM 唯一改进是
`WRITE_CHUNK_ROWS = 500` 分批插入，避免一次性拼超大 INSERT 撞 `max_allowed_packet`。

**本次改动**：新增 `createCoalescingPersistence()`（`backend/src/mysql-store.ts`），
把「同一次落库执行期间到达」的 `store.persist()` 合并成一次。

- 第一个请求**立即开跑**，不引入任何延迟（leading edge）；
- 执行期间到达的请求只置 `dirty`，本轮结束后统一写一次（trailing edge）；
- 每轮开跑时才取内存快照，所以第二轮必然包含期间全部变更；
- 每个 `persist()` 返回的 Promise 仍在该批数据真正落库后才 settle，`await` 契约不变；
- `close()` 会先 flush 剩余变更再放行等待者，避免关停丢写。

**实测对比（5 次 PATCH 客户）**

| 场景 | 改动前（推算） | 改动后（实测） |
|---|---|---|
| 5 个并发写 | ≈765 条 SQL | **321 条**（合并为 2 轮落库） |
| 5 个顺序 `await` 写 | ≈765 条 | **729 条**（各自落库，语义未变） |

「顺序 await 不被合并」是有意为之：合并掉会丢失中间状态。

### 3.2 获客读接口裸调 `readBarrier()`

`readBarrier()` 不传窗口 = 每次全量重读约 30 张表（run 状态 + agent jobs + 执行状态 + 模型配置 + provider 目录/连接）。

- `routes/prospecting.ts`：**20 处**改为 `readBarrier(1_000)`
- `routes/prospect-list.ts`：1 处 GET 接口改为 `readBarrier(1_000)`

保留裸调的位置（有意为之，属调度/写路径，需要真实最新数据）：
`prospect-scheduler.ts:81`、`prospect-queue-coordinator.ts:165`、`prospect-execution-kernel.ts:4860`、
`prospect-super-search.ts:1305`（5 秒 tick，且默认不启动）。

## 四、体验验收（2026-11-13 补测）

写合并改的是并发落库路径，风险不在"慢"，而在"用户看不到自己刚存的东西"。因此专门做了两层验证：
接口层（`scripts/verify-perf-ux.sh`，15 条）与界面层（`scripts/verify-perf-ux-ui.mjs`，17 条），并做了一次 A/B 对照。

### 4.1 A/B 对照（`scripts/ab-perf-coalescing.sh`）

同一批指标，`git stash` 回退 `mysql-store.ts` 后再测一遍，排除"没对比就下结论"：

| 指标 | 优化前 | 优化后 |
|---|---|---|
| 单次写延迟（3 次均值） | 52ms | 39ms / 50ms |
| 5 个并发写总耗时 | 218ms | 127ms / 113ms |
| 写后立刻读一致 | ✅ | ✅ |
| 1 秒后已落库 | ✅ | ✅ |

结论：**没有任何用户路径变慢**；并发场景反而快了约 45%（合并生效）。写后读一致在两种实现下都成立——
因为 MySQL 模式下 store 的内存镜像才是读路径的真相源，落库只影响持久化，不影响读。

### 4.4 两个容易误判的坑（已写进脚本注释）

1. **空闲采样必须先静置**。紧跟写操作采样会抓到 persist 的余波（曾误判成"空闲期 16 条 DELETE = 空转"）。
   静置 15s 后稳定为 `delete=0 / insert=0`。
2. **判断"空转全量重写"要看 `Com_delete`，不是 `Questions`**。一次 `persistAll` 必然产生 93 条
   `DELETE FROM`（`replaceRows` 无条件先删再插），所以 `Com_delete=0` 是"队列没空转"的铁证；
   而 `Questions` 里混着实例锁探活、连接池等固定开销（本地约 5 QPS，生产 0.18 QPS），拿它当阈值容易误报。

## 六、遗留（未做，需单独立项）

1. **P1｜增长型表改 append-only upsert**：`customer_activities`、`lead_activities`、`whatsapp_messages`、
   `wecom_messages`、`trade_documents` 等只增不减的表，不该跟着全量重写。
2. **P2｜按写接口声明变更表**：根治方案。让每个写路由声明「本次动了哪几个数组」，只写这几张表。
   工程量大，需重新设计 store 写契约。
3. **P4｜客户 / 供应商列表分页**：目前一次返回全表（单据列表已有 slice 上限 5000/100/9）。
4. **`prospect-super-search.ts` 的 5 秒 tick 全量重读**：默认随隐藏模块关闭；若将来开启
