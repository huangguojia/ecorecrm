# 数据隔离测试：A / B 业务员与管理员

> 执行时间：2026-11-05 09:4x
> 环境：前端 `127.0.0.1:5189`、后端 `127.0.0.1:4290`、MySQL `ecore_crm`、公司 `europe`

## 一、测试账号

| 账号 | 邮箱 | 密码 | 角色 | 能力来源 |
| --- | --- | --- | --- | --- |
| 管理员 | admin@goodjob.com | goodjob123 | 公司管理员 | 内置账号（74 项能力位） |
| A | a.isolation@goodjob.com | goodjob123 | 业务员 | IAM 新建成员 |
| B | b.isolation@goodjob.com | goodjob123 | 业务员 | IAM 新建成员 |

A / B 通过 `POST /api/v1/members` 由管理员创建（`tenantId=europe`、`roleId=legacy_sales`），返回：

- A：`userId=user_9106ecba…`、`membershipId=mem_0e0cd125…`
- B：`userId=user_8e38acef…`、`membershipId=mem_6832cf31…`

两者 `customer.read` / `customer.create` 的数据范围均为 `self`，`iamDataScope` 为 `null`（未走租户级数据范围）。

## 二、隔离验证矩阵

| 检查项 | A | B | 管理员 |
| --- | --- | --- | --- |
| 登录后可见导航 | 15 项（无权限管理、无系统日志） | 15 项（同 A） | 25 项 |
| 客户列表可见条数 | **1（仅自己的）** | **1（仅自己的）** | **6（全部未成交）** |

| `GET /api/customers/:id` 读对方客户 | 404 | 404 | 200 |
| `PATCH /api/customers/:id` 改对方客户 | 404「客户不存在」 | 404「客户不存在」 | 200 |
| 控制台报错 | 0 | 0 | 0 |

### 关键证据

- A 的客户列表：`UI-A-163946`，副标题 `德国 · Contact-A · Isolation A`
- B 的客户列表：`UI-B-163946`，副标题 `德国 · Contact-B · Isolation B`
- A 用搜索框输入 `UI-B-163946` → 0 条
- B 用搜索框输入 `UI-A-163946` → 0 条
- 管理员列表包含 `UI-A-163946` 与 `UI-B-163946`，两行分别标注 `Isolation A` / `Isolation B`

## 三、归属展示

| 位置 | 展示方式 |
| --- | --- |
| 客户列表 · 客户简称下方 | `国家 · 联系人 · 负责人`，第三段即归属人 |
| 客户全景页（点「全景」） | 明确标签：`德国 · Contact-B · 负责人 Isolation B` |
| 列表表头 | **没有独立的「负责人」列**，归属混在副标题小字里 |

结论：管理员**能**确认每个客户归谁，但列表页需要逐行读副标题第三段，不如独立列直观。

## 四、结论

1. **数据隔离成立**：业务员之间互相不可见，列表、搜索、详情、写入四条路径都拦住了，越权返回 404 而非 403（不泄露资源是否存在）。
2. **管理员全量可见**：同公司范围内所有客户都能看到，包含新建的 A/B 客户与原有客户。
3. **归属可追溯**：接口层返回 `ownerId` + `ownerName`，界面在列表副标题与详情页都能读到。

## 五、供应商：团队共享（不做隔离）

供应商与客户相反，是**团队资产**，按 `teamId` 取全量，不再按 `ownerId` 过滤。后端在 `GET /api/suppliers` 里就写明了这个取舍：

```ts
// 供应商是团队资产：按 teamId 取全量，不再按 ownerId 二次过滤
// （否则创建人离职/停用后，他录入的供应商会从列表里整批消失）
const suppliers = await repository.list(req.user!.teamId);
```

实测：

| 检查项 | A | B | 管理员 |
| --- | --- | --- | --- |
| 初始可见供应商 | 3 家 | 3 家 | 3 家（完全相同） |
| A 新建 `SHARED-SUP-*` 后 | 4 家 | **4 家（立即可见）** | 4 家 |
| 界面行内容 | 逐行一致 | 逐行一致 | 逐行一致 |

即 A 录入的供应商，B 无需任何操作就能看到并复用，符合「供应商共享、客户隔离」的预期。验证用的临时供应商已删除，库中恢复为原有 3 家。

## 六、同名客户互斥（本轮新增）

原来的查重只查「同团队 + 公司名 + 国家」，范围是对的，但提示只写「客户已存在」，业务员会以为是自己重复录入，换个写法再建一次——同一家客户在库里出现两条，商机金额分到两个池子。

现在把**归属人**一起算出来，并在界面上贴到公司名旁边。

### 判定

| 撞到谁 | 提示 |
| --- | --- |
| 别人名下 | `客户已存在：「X」（德国）已由 Isolation B 建档，不能重复添加；需要协作请联系该同事，或等他放入客户公池后领取` |
| 自己名下 | `客户已存在：「X」（德国）已在你自己名下，不能重复添加` |
| 公池客户 | `客户已存在：「X」（德国）目前在客户公池（原归属 Shirley），请先去公池领取后再跟进` |
| 成员已离职（users 里查不到） | 回退为`其他同事`，不编造姓名 |

响应体同时返回 `errorCode: CUSTOMER_DUPLICATE`、`existingId`、`ownerId`、`ownerName`。

### 覆盖面

| 场景 | 结果 |
| --- | --- |
| A 新建 B 已有的客户 | 409，提示 `已由 Isolation B 建档` |
| B 新建 A 已有的客户 | 409，提示 `已由 Isolation A 建档` |
| 管理员新建业务员已有的客户 | 409，提示该业务员姓名 |
| 大小写 / 首尾空格不同（`  ui-b-163946  `） | 仍判为同名（归一化后比较） |
| 同公司、不同国家 | 允许创建（查重键是「公司名 + 国家」） |
| **编辑改名**撞到别人的客户 | 409，同一套提示（本轮补上，之前改名不查重） |

### 界面

- 弹窗**不关闭**，公司名输入框套红色描边、内容全选
- 提示文字贴在输入框正下方，红色加粗
- 右上角同步弹 toast

> 踩坑：主题层有一条 `input:not(…)` ×4 的 `border-color: #262626 !important`，特异性 (0,4,1)，普通 `.is-invalid` 类压不住。第一版描边没生效，改成内联 `style.setProperty(..., "important")` 才稳。
